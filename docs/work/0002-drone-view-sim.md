# 0002: Drone view sim

**Status:** in-progress
**Touches:** apps/drone-sim, services/demo-data, services/drone-runtime,
tools/asset-builder, assets, packages/contracts

## Goal

For the demo, a desktop app follows one drone and shows in real time what that drone's camera sees,
rebuilt in 3D from the Demo Data scenario, with the risks its model reported boxed (red on fire,
yellow at risk). The app only renders: drone positions and detections come from Drone Info, the
world and sensor frames from Demo Data.

## Decisions

- The sim is a pure viewer. Drone movement and detection belong to drone-runtime; the sim takes
  positions and detections from Drone Info, the only service that streams drone state to viewers.
  Rejected (first version): a direct WebSocket link from the sim to each drone, with UDP discovery.
- Dummy data lives in the sim behind the same `DroneInfoSource` interface as the real client, so
  swapping to drone-info is a URL setting. The dummy plays back fixed routes rather than flying, and
  its detections are Demo Data's own hotspot readings, so no detector runs in the sim.
- The world is reconstructed server-side in Demo Data (numpy, the data already lives there) and
  shipped as static assets. The fire is animated client-side from per-cell timing using the same
  curves as `model/state.py`, so it moves smoothly without per-minute requests.
- Ground stays flat at the drone's ground level, matching Demo Data's camera model, so the 3D view
  lines up with the frames the detector saw (checked to within 1.5 px in
  `apps/sim/src/view/droneCamera.test.ts`).
- Boxes in the 3D view are re-projected from each detection's ground outline every frame rather than
  drawn in frame pixels, so they stay on the fire while the drone moves between frames.
- The demo scenario is a town plus grassland, not a forest (about 5 % tree cover), so the tree rules
  are strict on grassland and loose in tree cover. The same rules apply unchanged to a forest.
